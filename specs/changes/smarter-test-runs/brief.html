Smarter test runs

Forge change smarter-test-runs

TL;DR

A Forge change today can run the whole test suite three to seven times, and several sessions on the same project run it at the same time, which slows the machine enough to produce fake failures. After this change each project's full suite runs once per change, only one session runs a full suite at a time, and fake failures from load are checked by re-running just the failing files.

What you'll get

  • When two or three Forge sessions work on one project, even in separate worktrees, their full test runs take turns. A waiting session says whose run it is waiting for.
  • Verify runs the full suite once. Fixes made afterwards (leftover sweep, review) run only the tests for what they touched.
  • If a full run fails, only the failing files are re-run. If they pass on their own, the failures were caused by load and the change can move on without another full run.
  • At the end of each task group, the tests related to that group's changes run, so problems show up before verify.
  • forge status tells you honestly whether the full run passed, passed after a failing-files re-run, or failed.
  • Sessions remember the starting commit of nested repositories (like volo_web), so "tests changed since the start" works there too.
  • A false "session file was tampered with" error that showed up under heavy load is fixed.

How it works

Every full run goes through forge evidence --tier3. That command now takes a lock file stored in the repository's shared git folder, so all worktrees see the same lock. Runs of the smaller kinds (failing files, fix tests, group tests) are labelled and skip the lock. forge status reads the labels to decide whether the full run counts as passed.

flowchart TD
  G[Task group closes] --> R[Run tests related to the group's diff]
  R --> S[Verify: leftover sweep and its fixes]
  S --> L{Full-run lock free?}
  L -- no --> W[Wait, naming the holder] --> L
  L -- yes --> F[Full suite, once per project]
  F -- green --> D[Review]
  F -- red --> O[Re-run only the failing files]
  O -- green: load only --> D
  O -- red: real failure --> X[Fix, re-run those files] --> D
  D --> Y[Review fixes: only the tests they touch]

What changes for you

  • Nothing to configure. The lock is automatic.
  • You may see "tier-3 lock held by <session> (pid …) — waiting" in a session's output. That is expected.
  • If a crashed run ever leaves a lock behind and its process id was reused by another program, delete the lock file named in the message.

Risks and open questions

  • The lock only covers full runs started through Forge. A test command an agent runs directly is not coordinated.
  • "Run the full suite once" is a rule in the instructions, not something the tool blocks. Reviewers can see every run's label in the evidence.
  • If two sessions both find the same dead lock at the same moment, both may run once. This only costs time.
  • The tool trusts the agent's list of failing files for the re-run. The final reviewer checks it against the failed run's output.

Out of scope

  • Choosing test commands for a project. Forge documents the Jest/Vitest options; the project's own commands stay the agent's choice.
  • Changing pace presets.
  • Showing lock holders in forge fleet.
  • A project's full end-to-end smoke suite. That belongs in CI; Forge runs only the change's own steps.
