Making a recorded e2e harness work on someone else's machine

Operator brief — change harness-setup-probe

TL;DR

When Forge records a project's e2e harness, it currently saves how to start the app and nothing else. It doesn't save the command that proves the harness works, and it doesn't save what the machine needs installed for that proof to run. So an agent can install a browser in its own sandbox, watch the tests go green, report "harness proven" — and the next human to clone the repo hits an error the agent never saw.

This change adds two optional pieces to the recorded harness (setup and probe), shows them everywhere the harness is displayed, and makes a failing test loop point at the setup command instead of leaving you to guess.

What prompted it

A team recorded a Playwright harness. Forge proved it green in the agent's environment. On the operator's own laptop the very first test run failed with "browser executable doesn't exist — run npx playwright install". The harness had captured how to boot the product, but not how to make the thing that tests the product exist.

What you'll get

  • A harness can now remember the command that proves it — so a later session verifies the harness instead of re-inventing how to test it.
  • A harness can now remember what this machine needs installed — browsers, drivers, container images, language toolchains. Anything that lives on a machine rather than in the repository.
  • When a test loop fails and a setup command is on file, the output names that command as the first thing to suspect. That turns a confusing "the tests are broken" moment into "ah, I haven't run the one-time install on this checkout yet."
  • A written rule in the Forge skill: a harness proven only in the agent's environment is not proven. If an agent installed something to make the test pass, that install has to be recorded.

How it works

The recorded harness is a small block of JSON in the project's committed .forge/config.json. Today it holds a description, a start command, and a location. This adds two optional siblings. Nothing is auto-detected and nothing is auto-installed — Forge records what it is told and repeats it back at the moment it is useful.

What changes for you

BeforeAfter
forge e2e harness --set "…" --start "…" --dir e2e same, plus optional --probe "npm run test:e2e" and --setup "npx playwright install chromium"
Harness display shows Start and Location shows Setup, Start, Probe, Location — in the order you'd actually run them
A red loop shows only the failing step a red loop also names the recorded setup command, when there is one

Existing harnesses keep working untouched — both fields are optional, and a harness recorded without them prints exactly as it does today.

Risks and open questions

  • The hint can point at the wrong thing. A step that fails for an ordinary code reason still prints the setup line whenever a setup is on file. It's worded as a suspicion, printed once at the end rather than per step, and it never changes the exit code — the failing step stays the headline. Watch whether it becomes noise; if it does, the answer is to soften the wording, not to start guessing which failures are environmental.
  • Recording is still voluntary. Nothing forces an agent to pass --setup; the skill text carries that obligation, the same way it already does for --start.
  • Deliberately not solved: Forge does not verify that the setup was actually applied. That would mean teaching it how to check every tool it might encounter.

Out of scope

  • No tool detection. The original suggestion had Forge look for Playwright in package.json and check for installed browsers before proving the harness. That means a bespoke check per tool — Playwright, then Cypress, chromedriver, Docker, Go — each one able to go stale when the tool changes its CLI. The probe already fails with the tool's own error message; Forge's job is to explain that failure, not to predict it.
  • No auto-install. Setup commands are large downloads by nature. Forge prints the command; you decide when to run it.
  • No third field for prose. The suggestion included a separate human-readable hint alongside the setup command; the harness description already covers that.

Work overview

1. Record and surface (2 tasks) New flags, stored and printed wherever the harness is shown.
2. Attribute failures (1 task) The suspicion block on a red loop, and the three cases where it must stay silent.
3. Teach the rule (3 tasks) Skill reference, both editor command templates, usage docs and changelog.
4. Prove it (2 tasks) A real end-to-end loop driving the shipped CLI against a scratch project — and recording that loop as this repo's own harness, which it currently lacks.
