Forge commands disagree about which session they are acting on

And the one that matters most — the money/auth gate — gets it wrong silently.

The problem, in one paragraph

.forge/active.json records "the active session". It is written by forge new and nothing else, so it actually means most recently created — not the session you are working on. Twelve commands read it when you do not pass --session.

What that costs, measured

Two sessions open, the pointer naming the wrong one, driven through the real CLI:

CommandWhat happens
forge phase done Gates the wrong change. It scores the neighbour, writes its scorecard and its permanent ledger line. The high-risk change it was meant to judge ends at implement with no verdict, no scorecard, and no record it was ever gated. The final-review floor never runs at all.
forge phase verify Reopens a finished neighbour (done → verify).
forge status, session-start hook Agree with the pointer, so nothing on screen contradicts the wrong answer.

Why you are seeing this as a separate change

It was found while shipping 0.3.29 (review authorship measured from the host's dispatch record), which needed to know which session a reviewer was dispatched for. That release fixed it for its own command — forge review-label refuses rather than guessing — and left the rest of Forge as it was.

Absorbing the general fix took a two-file change past thirty files. It is a different bug, it is larger, and it deserves its own review. That is this change.

What you will get

  • One place decides which session a command acts on. --session always wins. If more than one session is unfinished, or the sessions directory cannot be read, the command refuses and names each candidate as the flag that selects it. The pointer wins only when it names unfinished work.
  • The pointer follows the work. forge phase marks the session it transitioned — below every gate, so a refused transition does not move it, and never on done/skipped, so finished work cannot capture your status line or the resume hook.
  • A failed pointer write says so instead of being swallowed.
  • Writes to .forge JSON become atomic. Measured with two concurrent writers: 62 torn reads in 79 on a plain write, 0 over a rename. It only starts to matter once the pointer is written on every transition.

What changes for you

$ forge phase done          # two sessions open, no --session
Refusing to guess which session to act on — 2 sessions are unfinished.
  --session 20260729T…-billing    (add-refunds, verify)
  --session 20260728T…-search     (search-index, implement)

Re-run naming one, e.g. forge phase done --session <id>.

The refusal applies to done and finish only. Those two write the scorecard, the permanent ledger line and the money/auth verdict — being wrong there is unrecoverable. Every other phase warns and carries on: 

$ forge phase implement     # two sessions open
[forge] Warning: 2 sessions are unfinished; acting on 20260729T…-billing (add-refunds).
[forge] Pass --session <id> to act on 20260728T…-search instead.

Being wrong about which session is at implement costs a re-run. Refusing there would be an obstruction rather than a guard. With a single session open, nothing changes at any phase.

Risks

  • The warning path can still act on the wrong session at implement or verify — deliberately. It says which one it chose and how to choose the other; it does not stop you. Only the two phases that write a permanent record refuse.
  • It touches set-phase.mjs and lib.mjs — the two files everything else depends on.
  • Four of these guards were written once already and were unpinned — the mutant survived. Every one is re-proven by mutation here rather than trusted because its test passes.

Out of scope

  • Anything about review authorship — that shipped in 0.3.29.
  • Multi-session workflow features (switching, listing, naming). This only makes the existing resolution honest.
