Session telemetry & analysis

What a Forge session will remember about how it actually ran.

TL;DR

Today a finished session records how disciplined it was — a score, which reviews happened, what got deferred — and nothing about how it actually ran. This change starts keeping the other half: how many tokens it burned, which models did the work, how often tools failed, and how often a subagent was launched with a model the policy would not have chosen. Almost none of it needs new plumbing, because the coding agent already writes all of it to disk; Forge just has to read it before that record is deleted.

What you'll get

  • Every finished session leaves a small metrics file: token counts, the models that ran, tool failure rate, one row per subagent, and where the effort went by phase.
  • Those totals are copied into the permanent session ledger, so they survive cleanup deleting the session folder two weeks later — the same trick already used for scores.
  • A new forge analyze command prints the history back as numbers: a table per session, a table per model, and where the tokens went.
  • You can finally see how often the model policy is bypassed — every time a subagent is dispatched with a model the resolver would not have returned, it gets counted.
  • The existing /forge:analyze report gets these numbers as its input instead of reading tea leaves from session folders.

How it works

The coding agent already keeps a full transcript of every session on disk, and that transcript records — per request — the model used, the tokens spent, and whether each tool call failed. Subagents get their own transcript files alongside it. The session's own identifier is available in the environment Forge commands run in, so a session can note which transcripts belong to it without installing anything.

When a session finishes, Forge reads those transcripts, keeps only the lines belonging to that session's lifetime, adds them up, and writes the totals. Nothing is recorded while you work; there is no new hook to install and nothing to keep wired. The one exception is subagent dispatch: a dispatch that gets blocked leaves no transcript behind, so the existing model-policy check — which already inspects every dispatch — notes its own decisions as it goes.

The subtlety that shaped the design. The transcript writes one line per piece of a reply — the thinking, the text, each tool call — and repeats the same token count on every one of them. In a sample session that was 39 lines for 12 real requests. Adding them up naively would triple every number while still looking entirely believable. Counting once per request is treated as a correctness rule with its own dedicated test, not a detail.

What changes for you

CommandWhat it does
forge analyzeNew. Prints session, model and phase tables from the recorded history. Writes nothing.
forge analyze --jsonSame numbers as raw data, for the /forge:analyze report to consume.
forge metrics collectNew, rarely typed by hand — runs automatically when a session finishes.
/forge:analyzeUnchanged to use, but its report is now based on measured numbers.

Nothing else changes. No new hook to install, no settings to merge, no change to how sessions are created or run. Sessions that already exist stay valid and simply have no metrics.

Risks and open questions

  • It reads a file format nobody promised to keep. The transcript layout could change in a future release of the coding agent. All knowledge of the format is kept in one module, the observed version is recorded with every result, and anything unfamiliar is reported as "unavailable, here's why" rather than guessed at. A format change loses telemetry; it cannot break Forge.
  • Claude Code only, for now. Sessions run through Cursor or Codex will record no metrics and say so. Adding them later is additive work.
  • Two clocks. Transcripts are cleaned up after about a month, Forge sessions after two weeks. Collection happens when a session finishes, comfortably inside both — but a session that is abandoned rather than finished will have nothing to collect.
  • Silence is possible. Because none of this may ever block your work, a failure is recorded quietly rather than shouted. forge analyze therefore always leads with how many sessions it could actually see, so a thin history is never mistaken for a complete one.
Deliberate boundary: these numbers never touch the session score. The score measures discipline; this measures cost. If cheaper sessions scored higher, the incentive would be to reach for weaker models — the opposite of the standing policy on this project.

Out of scope

  • No money. Tokens are counted; no price table, no dollar figures. Prices go stale and the numbers would mislead on a subscription. Cost stays derivable later.
  • No backfill. The three sessions already in the ledger stay blank rather than being attributed by guesswork.
  • No trend detection or automatic findings yet. This change produces the numbers; deciding which shifts are worth an alert comes after we've seen some real ones.
  • Nothing about your content is recorded — no prompts, no replies, no commands, no file contents. Counts, model names, tool names and timestamps only.
