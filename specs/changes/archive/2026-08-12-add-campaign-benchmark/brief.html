Campaign benchmark

Operator brief — change add-campaign-benchmark

TL;DR

Our current benchmark says Forge doesn't help. Across the 54 paired runs we've already done, 47 came out exactly level, 6 favoured the plain agent and 1 favoured Forge — while Forge cost 5.7x more. That's not because Forge is useless; it's because the tasks are one-shot puzzles that finish inside a single sitting, which is the one situation where Forge's discipline buys nothing.

This change builds a second benchmark shaped around what Forge actually claims: six change requests against one codebase, delivered one at a time, each handled by a brand-new agent that inherits nothing but the repository the last one left behind.

What you'll get

  • A new benchmark you can run that measures whether work survives a handoff, not whether one puzzle got solved.
  • Scores as counts ("met 7 of 10 requirements") instead of a single pass/fail bit, so partial progress is visible.
  • A regression score at every step: every earlier request's checks re-run, so you can see work getting broken.
  • A "claimed done but wasn't" signal, worked out mechanically rather than by reading what the agent said.
  • A report broken down by step number, so "the gap widens with each handoff" is a line you can draw.

How it works

One small order-and-payments service. Six requests in a fixed order. Each request runs in a fresh container with a fresh agent — no memory, no transcript, no summary. The only thing that travels forward is the repository itself. Forge leaves specs, tests and a wiring record in there; a plain agent leaves code. That difference is the whole experiment.

The six requests, and what each is looking for:

#RequestWhat it probes
1Orders, charging, and a status flow (pending → paid → shipped → delivered, plus cancelled)Sets the rules everything later can break
2Partial refunds against step 1's ledgerOrdinary building-on-top work
3Trap: "refunds may be issued on cancelled orders" — which contradicts step 1Does it flag the clash, or quietly pick one and poison everything after?
4Idempotency keys on every endpoint that changes somethingTouches every route built so far
5Refactor: split the handlers up, behaviour unchangedThe operation agents are measurably worst at — one study found only 30–37% of LLM refactors were functionally correct
6Trap: auto-expire stale orders after 30 daysThe obvious implementation expires already-paid orders, breaking a rule from step 1 that nothing directly tests
Two rules keep the scoring honest. The hidden checks only ever talk to the service over HTTP — they never reach inside and call a module directly. So a feature that was written but never plugged in simply fails, and we get wiring coverage without a separate metric. And when a request can't be met without breaking an earlier one, the agent is told to write a BLOCKED.md file naming both. That keeps the trap steps gradeable by a machine, and keeps our existing rule that we never treat the agent's own summary as the source of truth.

What changes for you

  • A new corpus name to pass to the runner: forgekit-campaign-v1. The existing corpora and commands work exactly as before.
  • A new offline check, npm run smoke:evals:campaign, that validates all six steps without touching a model.
  • The aggregate report gains a per-step breakdown. Existing single-task output is unchanged.
  • A full run is about $38 and roughly 4 hours (6 steps × 2 arms × 2 repetitions, one at a time). That's a separate decision you authorize — building the benchmark spends nothing.

Risks and open questions

  • The effect might not show up. Six steps may be too few for problems to accumulate, and step 3's contradiction may be obvious enough that both arms catch it. Both were flagged during design and accepted; eight steps would cost roughly $50 and 5.5 hours if we need to grow it.
  • Carrying the repo forward is the riskiest part. If that step quietly fails, every request becomes a fresh start and the results would still look plausible. So carryover gets its own check: a missing inheritance is reported as a broken run, never as a score of zero.
  • The scoring change touches the existing benchmarks. Old result files must keep loading unchanged, and the frozen v1 corpus must still match byte for byte.
  • The corpus is public, like the existing ones, so we can't rule out that a model has seen it.
  • Building it proves nothing on its own. Only an authorized, pre-registered run produces evidence.

Out of scope

  • Changing the existing hard-v2 benchmark. It stays frozen — its 54 pairs remain a valid record that one-shot tasks show no difference.
  • A control arm where both sides restart from clean code each step. It would double the cost, and the thing it removes is the effect we're claiming.
  • Mutation testing.
  • Working out why carrier-event-reconciliation fails in both arms every time. Filed separately.
