Making escape tracking work on real projects

TL;DR

Escape tracking counts how often a finished Forge change needs fixing within two weeks. Today it misses all of Volo's code, because that code lives in separate git repos inside the project, and every possible escape waits for you to confirm it by hand. After this change it searches every repo (including Volo's history), proves escapes automatically when the fix came with a test, and records which Forge release and which models did the work.

What you'll get

  • forge escapes finds fixes in Volo's volo_web and volo_mobile, for new sessions and, estimated from timing, for past ones (shown separately as "inferred").
  • forge escapes verify runs the fix's own test on the code before the fix and after it. If it fails before and passes after, the escape is confirmed for you. If not, the candidate stays with you, labelled with why.
  • Each finished session records the Forge version and which model coordinated vs which models did the subtasks, and forge escapes report --by version shows the escape rate per release.

How it works

When a session finishes, Forge notes where each repo started and ended. Later, any fix that rewrites lines from that range is a candidate. For verification, Forge makes a throwaway copy of the repo at the old code, drops in the fix's test, runs your configured test command, then does the same at the fix. Your own working files are never touched, and the copies are always removed.

flowchart LR
  D[Session done] --> R[Range per repo recorded]
  R --> C[Later fix rewrites those lines: candidate]
  C --> V{forge escapes verify}
  V -- test fails before, passes after --> A[Confirmed automatically]
  V -- passes before --> N[Not reproduced: you decide]
  V -- needs code the fix added / fails after --> E[Environment: you decide]
  V -- no test or no rule --> U[Undecided]

What changes for you

  • To use verification in a project, add test commands to .forge/config.json under escapes.replay, for example "files under volo_web/server/ run with npx jest {file} in that folder". Forge never guesses the command.
  • Verification runs only when you ask (forge escapes verify), and only with the same permission to run commands that forge evidence needs.
  • The glossary's "Commit range" now means a range per repository.

Risks and open questions

  • A fix's test may need code the fix also added, so it fails on the old code for the wrong reason. Forge recognises "module not found" and syntax errors and labels those "environment" instead of confirming.
  • The throwaway copies borrow today's installed packages; if the old code needs different versions, that shows up as "environment", not as a false confirm.
  • Inferred ranges for past sessions are estimates by time; that is why they are shown separately.
  • Any automatic confirmation can still be overturned with forge escapes dismiss.

Out of scope

  • Comparing Forge with plain sessions on confirmed escapes (escape replays as evals) — next step once escapes are confirmed.
  • A scheduled weekly fleet report.
  • Changing the two-week window or what counts as a candidate.
