Finish the ENOENT split

Findings F56 & F57 · change finish-the-enoent-split

TL;DR

The previous change taught Forge to stop confusing "this file isn't here" with "I couldn't open this file" when it looks for a conversation's records. Its own reviewers then found the same confusion surviving in two smaller places: the function that reads a found file still swallows every failure into "the file was empty", and when nothing at all can be opened, Forge still tells you the records were "pruned" when they were actually blocked. This change finishes the job. No decision Forge makes changes — only how honestly it reports what it saw.

What you'll get

  • A session whose history file exists but can't be read no longer silently vanishes from the token totals — it's named in the metrics document, every time, not just when something else already looked suspicious.
  • When Forge stands aside at the review gate because it couldn't read anything, the message tells you what was blocked and where — instead of claiming the records were cleaned up.
  • Less code: the previous change worked around the reading problem with a second, duplicate file-read. That workaround is deleted, because the read itself now answers.

How it works

Reading a session's history has two steps: find the file, then read it. The previous change fixed honesty at the finding step. This one fixes the reading step: instead of returning "no lines" for a missing file, a blocked file, and a genuinely empty file alike, the reader now says which of those happened. 

flowchart TD
    A[Read the found file] --> B{What happened?}
    B -->|Read fine, has lines| C[Count them]
    B -->|Read fine, empty| D[Count nothing — honestly nothing there]
    B -->|Could not read| E[Say so: which file, what error]
    E --> F[Metrics name the session as uncounted]
    E --> G[Gate messages say blocked, not pruned]

One judgment call worth knowing about: at the finding step, a missing file is normal — old conversations get cleaned up routinely, and the search probes many places where a file simply isn't. At the reading step, the file was located a moment ago, so "suddenly missing" is not normal and is reported like any other failure. The two layers deliberately have different rules, and the code says so.

What changes for you

  • No new commands, no new flags, and no gate decision changes — only the wording of "why" messages and the completeness of the metrics record.
  • A metrics document may now name a session as uncounted in cases that were previously invisible.

Risks and open questions

The reading function sits on the forge phase done path Its shape changes. All five users of it are in this repo and updated together; a missed one fails loudly (a crash), not quietly (a wrong number). The identical move was made for the finding step last change and shipped clean.
"Empty" must not start reading as "failed" A genuinely empty history file is a successful read of nothing. The previous change pinned this with a test that must stay green untouched, and the audit will attack it with a mutation that deliberately confuses the two.
Deliberately out of scope: nothing yet displays the uncounted-sessions record (forge analyze and the fleet report don't show it); the cleaned-up-records limit from the previous change stays with its owner (F12).
