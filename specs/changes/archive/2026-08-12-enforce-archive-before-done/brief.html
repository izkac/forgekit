Enforce archive before done

Operator brief · change enforce-archive-before-done

TL;DR

Finishing a piece of work has a filing step, and nothing checks that you did it. Two changes shipped to users this month with that step skipped, which left the project's specifications describing behavior that was already two releases out of date. This change makes the finish command stop and tell you when the filing step is still outstanding.

What you'll get

  • Marking work finished stops with a clear message if the change hasn't been filed away yet.
  • The message tells you the exact command to run — no looking it up.
  • If you genuinely want to leave something unfiled, you say so in writing and that reason is kept on the record permanently.
  • Nothing changes while work is still in progress — the new check only speaks up at the very end.

How it works

Filing a finished change does two things: it folds the change's new requirements into the project's main specifications, and it moves the change's folder into an archive. Skipping it is invisible today because the finish check was built to read from either location, so it genuinely cannot tell the two states apart.

The fix adds one question at the finish line: is this change's folder still sitting in the active area? If yes, stop. That question is asked only at the finish line, never during the work itself — an unfiled change is perfectly normal right up until the end.

Risks and open questions

This makes an existing step stricter. Anyone part-way through work when this ships will meet a new stop at the finish line. It is a one-command fix and the message says which command, but it is a real change in behavior and worth knowing about before it lands.
  • The written-reason escape hatch is deliberately separate from the existing "this work is unfinished" override, so the records don't end up claiming work was incomplete when it was actually done and just not filed.
  • If a change somehow exists in both the active area and the archive, the check treats it as unfiled and stops. That is the intended call — something is genuinely out of place and a person should look at it.

Out of scope

  • The two changes that already shipped unfiled were filed by hand before this work started. There is no catch-up or migration step here.
  • There are two separate pieces of code that work out where a change's folder lives. This change reuses the better one and leaves the other alone; merging them is its own job with its own risks.
  • Nothing about the filing command itself changes — only whether you're reminded to run it.
