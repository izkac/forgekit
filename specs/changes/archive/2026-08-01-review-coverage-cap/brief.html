Review coverage caps the grade

Operator brief — change review-coverage-cap

TL;DR

Right now a Forge session can score an A even when nobody except its own author ever read the work. Reviewing is worth only 5 points out of 100, so it can't move a grade. This change makes missing review coverage a ceiling on the score instead of a rounding error — the same way a failing product loop or an unfinished session already caps a grade today.

What you'll get

  • A session that dispatched no reviewer at all, on a pace that asked for one, can no longer score above a B — and no higher than a C if it also had no independent final review.
  • The scorecard, which outlives the session after cleanup, now records that absence in plain language instead of staying silent about it.
  • Sessions that did get reviewed are completely unaffected — 12 of this project's 18 past sessions don't move at all.
  • A guarantee, pinned by a test: doing more review can never score worse than doing less. That is the exact bug that forced the last attempt to be pulled.

How it works

After the score is totalled, one extra question gets asked: did anyone outside the author actually review this, and was review even expected? If review was expected and none happened, the score is pulled down to a ceiling. An independent final reviewer — someone who read the finished change as a whole — softens the ceiling but doesn't remove it, because reading the finished result is a different job from reviewing the work as it's built.

Why this can't repeat last time's failure. The previous attempt (0.3.25) was pulled because it was backwards: a session with zero reviews slipped past the check entirely and scored 95/A, while a session that did get reviewed was capped at 69/C. The cause was a counter that one code path never filled in. This version asks a question that is always answered on every path, and the very first test written is the zero-review case that broke last time.

What changes for you

  • If you have deliberately turned per-group reviewers off (forge prefs -- --set review.perTask=never), you are never capped for it.
  • Nothing new to run. forge score and forge phase done behave as before; only the number and the explanation change.
  • When a cap applies you'll see a line in the scorecard's Caps section saying which reviewers were missing and which ceiling was applied.
  • Past scores are not rewritten. Only sessions scored after this ships are affected.
  • Nothing is blocked. This costs a grade; it never refuses a transition.

Risks and open questions

  • Whether a review counts as "independent" is still judged by reading its text. If that reading is wrong in the strict direction, a session that was genuinely reviewed could lose a grade it deserved. Accepted knowingly: the cost is a grade, never a blocked transition — and the stricter alternative has already been tried and reverted twice for refusing correct work.
  • The 5-task floor is a judgement call. Below it, small changes are exempt, so a genuinely unreviewed 4-task change escapes. Chosen because Forge's automatic pace guess falls back to "standard" whenever it can't classify the work, and small unclassified changes shouldn't be punished for that.
  • Watch the first few sessions after this ships. If a session you believe was properly reviewed gets capped, that's a defect worth reporting, not a verdict to accept.

Out of scope

  • Counting how much of a change was reviewed. The cap only asks whether any reviewer was dispatched, deliberately — the existing "how many groups were covered" measurement has its own known defects (tracked separately) and this change is built so it doesn't depend on them.
  • Reworking how caps are recorded so an applied cap is distinguishable from a noted one. Known issue, tracked separately, unchanged here.
  • Rescoring or rewriting any historical session.
