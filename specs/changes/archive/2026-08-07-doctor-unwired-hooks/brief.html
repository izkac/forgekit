Doctor detects unwired hooks

TL;DR

Forge's enforcement rides on small hook programs that forge init copies into each project. But copying the files is only half the job — the agent (Claude Code, Cursor) only runs a hook that is also registered in its settings file, and that registration is a manual merge step that is easy to skip. When it is skipped, everything downstream is silently off: subagent model policy is not enforced, dispatches are not recorded, session reminders never fire — and nothing tells you. One real project (volo) ran 47 subagents with zero dispatches recorded in exactly this state; another (helm) ran its whole history with only one of four hooks registered. After this change, forge doctor catches the state, and every forge new warns about it.

What you'll get

  • forge doctor compares the hook files present on disk against what the agent's settings actually register, and fails with the exact list of unregistered hooks and the snippet file to merge.
  • forge new already runs doctor in warn-only mode — so a project in this state warns at every session start instead of staying silent for weeks.
  • The check keys off the files on disk, not a hardcoded list — a hook added by a future Forge version is covered automatically.

How it works

flowchart TD
    D[forge doctor] --> C{.claude/hooks/ exists?}
    C -->|no| S[surface skipped — ok]
    C -->|yes| F[list forge-*.mjs on disk]
    F --> W["walk hook commands in settings.json
    and settings.local.json"]
    W -->|every file referenced| OK[check passes]
    W -->|any file missing| FAIL["exit 1 — unwired: forge-model-hook.mjs, …
    merge .claude/forge-hooks.snippet.json"]
    N[forge new] -->|warn-only doctor| FAIL

The same logic covers Cursor (.cursor/hooks/ against .cursor/hooks.json). A project with no hooks directory for a surface simply skips that surface — init decides what a project wires; doctor only insists that what was scaffolded is actually live. A settings file that exists but cannot be parsed fails the check too, because at runtime it behaves exactly like an unwired one.

What changes for you

  • forge doctor can now fail (exit 1) in projects that previously passed while silently unenforced — that is the point. The fix it prints is the merge you were always supposed to do.
  • --warn-only (used by forge new) still exits 0; you just see the warning.
  • forge init is unchanged. Making init merge the settings itself is filed as a follow-up idea in the findings ledger.

Risks and open questions

  • A deliberately-parked hook file now fails doctor. The escape is to wire it or delete the file — an intentionally dead hook lying in the hooks directory is precisely the ambiguity the check exists to remove.
