Checkpoint scopes to this session's work

Operator brief · change fix-checkpoint-path-scope · finding F111

TL;DR

When two pieces of work are open in the same folder at once, the "save my progress" command grabs everything in the folder — including the other work's files — and records them under the wrong job. This change makes it save only the current job's files, and stop and ask when it can't tell them apart.

What you'll get

  • Saving progress no longer sweeps in a second open job's changes.
  • When two jobs are open and the tool can't tell whose change is whose, it stops and tells you, instead of guessing wrong.
  • A new way to say exactly which files to save (--path), so you can still save the current job's work while the other stays open.
  • It will never save another open job's planning files, even if you ask it to by name.
  • When only one job is open — the normal case — nothing changes at all.

How it works

"Save my progress" (a checkpoint) currently stages every change in the folder except its own scratch notes. It has one narrow guard that catches another job's brand-new planning files, but it misses edits that job made to shared code. So with two jobs open, one job's checkpoint quietly commits the other's edits.

The fix looks at whether a second job is open. If not, nothing changes. If one is, it only saves changes that clearly belong to the current job; anything it can't attribute makes it stop and point you at the fix — either name the files to save, or finish the other job first. 

flowchart TD
    A[forge checkpoint] --> B{Second job open in this folder?}

Risks and open questions

The tool can't read minds about shared code. A job records which plan it owns, but not which source files it edited — so when two jobs both touch loose source files, it genuinely can't tell whose is whose. It refuses rather than guess. The cost is an occasional "please name the files" when two jobs are open; the answer is right there in the message. It can never commit more than before — only the same or less.

Out of scope

  • No attempt to auto-detect which source files a job touched — that needs tracking the tool doesn't have.
  • No change to the push rules; checkpoints still never push and still refuse on the main branch.
  • The single-job case, which is almost every checkpoint, is deliberately left exactly as it is.
