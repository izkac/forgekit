TDD evidence guard

In one sentence: after this change, an agent can no longer quietly rewrite your existing tests, claim a test run it never made, or ship into a project where the enforcement hooks were never turned on.

Why now

Research across 2024–2026 (and our own 34-session scorecard data) agrees on one point: written rules for agents decay, mechanical gates hold. The best-documented agent failure mode is test gaming — editing or deleting tests so bad code looks green, then reporting success. Today Forge's TDD rules are all prose: nothing blocks a test edit, and the "evidence" that tests ran red-then-green is typed in by the same agent that did the work.

What gets built

1. A test guard. Tests that already existed when the session started become read-only for agents, from implement through finish. An edit attempt is blocked on the spot (Claude Code hook), and even on hosts without hooks, forge phase done refuses if a pre-existing test was changed without a recorded exception. New tests written during the session are unaffected — TDD needs those. When a legitimate change to an old test is needed, forge test-allow <file> --reason "…" records it; every exception is shown to reviewers and on the scorecard.

2. Executed red→green proof. A new command, forge tdd run, runs the test command itself and writes the result (command, exit code, time) to the task's evidence file. The agent can no longer transcribe an exit code — the CLI observed the run. Completing a session now requires each finished task to show a real failing run before its passing run.

3. Hooks wired by default. Until now forge init wrote a hooks snippet but left merging it into .claude/settings.json to you — the main reason some projects ran with zero enforcement. Init (and forge doctor --install) now merge it automatically, without touching your own settings entries.

4. An honest exit for work with no tests to run. Some tasks change documentation or configuration and have no red/green cycle at all. Those record forge evidence --task <id> --no-tdd --reason "…". The reason is required, it is written into the task's evidence file, and reviewers are told to judge it — claiming "docs-only" on a task that changed real behavior is a review finding, not a free pass. Recording evidence without either a red→green pair or this declaration will refuse at the end of the session.

What it feels like day to day

  • Normal TDD work is unchanged — write a new test, watch it fail, make it pass.
  • If an agent tries to "fix" an old test, it gets blocked and must ask you; your approval is one command and is visible at review time.
  • If the guard itself breaks, it fails open with a warning — it will never lock you out of your own session. The end-of-session integrity gate is the safety net that fails closed.
  • Old and in-flight sessions are exempt from the new red→green requirement; only sessions created after this ships are held to it.

What is deliberately out of scope

Two follow-ups from the same research roadmap land later: an independent test-writer subagent (tests authored by a different agent than the implementer) and a mutation-testing gate (proof that tests can actually catch bugs).
