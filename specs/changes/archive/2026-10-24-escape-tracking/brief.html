Escape tracking

Operator brief — what this change builds, in plain language.

TL;DR

Forge will start measuring whether its work actually holds up. When a session finishes it remembers which commits it made; later, forge escapes finds the commits that went back and changed that work within two weeks, and you mark each one as a real escape or not. Separately, every time a Forge gate refuses something, that refusal is counted, so in April we can see which gates never fire.

What you'll get

  • Every finished session records the commits it made (start and end), kept in the session ledger and the machine-wide fleet list, so it survives worktree deletion.
  • forge escapes lists, per finished session, later commits within 14 days that rewrite or delete lines that session added. Its own commits are ignored.
  • You confirm or dismiss each one with a single key (or a flag). Confirming needs a test that would catch the bug: the fix commit's own test, or one you name.
  • forge escapes report shows the escape rate per month, across every project on this machine.
  • forge fires shows how often each gate refused something, across every project, including gates that never fired.
  • Works on old history too: sessions finished before this change get their commits worked out from their checkpoint commits.

How it works

At done, the session's start commit and the current HEAD are saved. Later, for every commit after that window opens, Forge asks git who wrote the lines that commit removes or rewrites. If any of those lines came from the session's commits, the commit is a candidate.

flowchart LR A[forge phase done] -->|saves start..end commits| L[(sessions ledger + fleet list)] L --> E[forge escapes] G[(git history)] -->|later commits, 14 days, blame| E E -->|candidate| O{you: confirm / dismiss} O -->|confirm + replay test| X[(.forge/escapes.jsonl)] X --> R[forge escapes report: rate per month] F[any gate refusal] --> FL[(machine-wide gate-fires log)] FL --> FR[forge fires: count per gate]

What changes for you

CommandWhat it does
forge escapesLists candidates; in a terminal, steps through them one key at a time (c confirm, d dismiss, s skip, q quit).
forge escapes confirm <session> <commit> [--test path]Marks a real escape; refuses without a replay test.
forge escapes dismiss <session> <commit>Marks it not an escape; it won't be shown again.
forge escapes reportEscape rate per month across the fleet.
forge firesGate refusal counts per gate across the fleet.

Nothing else changes: gates refuse exactly as before; they now also leave one log line.

Risks and open questions

  • Squash-merged work can't be traced back by git and is skipped with a reason.
  • Old sessions without checkpoint commits have no known commits and are skipped, not guessed.
  • Candidates are suggestions: refactors and follow-up features also rewrite lines. That's why you decide.
  • The lease guard hook from the resource-leases branch is not counted yet; it gets wired after that branch merges.

Out of scope

  • Turning confirmed escapes into replay eval tasks under evals/harbor — a later change.
