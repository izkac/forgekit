Resource leases and worktree slots

Forge change resource-leases · operator brief

TL;DR

When several agent sessions work on one repository, even in separate worktrees, they still fight over shared things: the database, full test runs, dev-server ports. After this change, a project can name those resources once; Forge then makes sessions take turns on them and gives each worktree its own number, so database names and ports can differ per worktree instead of colliding. It works the same in the terminal, Claude Code, Cursor, Codex and orchestrators such as T3 Code, and it never overrides anyone's permission settings.

What you'll get

  • Run anything one-at-a-time across all worktrees: forge lease db -- npm run db:migrate. A second session waits, then runs; if it waits too long (9 min by default) it stops and says who holds the lease.
  • Wrap your own scripts once ("test": "forge lease tests -- vitest run") and every tool and every person running them takes turns automatically.
  • If an agent runs a contended command directly, Forge blocks it and tells the agent the wrapped command to use. It never approves or rewrites anything.
  • Nesting is safe: a wrapped script run under the same lease, or forge evidence inside forge lease, runs immediately instead of waiting on its own parent. (Added during implementation after a review found the trap.)
  • The existing "only one full test run at a time" rule keeps working; it's now just the built-in lease tier3.
  • Each worktree gets a stable slot number (main checkout = 0, others 1, 2, …). With templates like "PORT": "{3000+slot}", Forge writes .forge/slot.env for your tooling to load.
  • forge lease list shows who holds what; forge doctor warns when hooks can't find forge (common when an orchestrator runs as a background service).

How it works

A lease is a small lock file in the repository's shared git folder, so every worktree sees it. Holding one needs a running process, which is why commands run through forge lease. The hook only watches for agents skipping that step; when no leases are configured it does nothing at all.

flowchart TD
  A[Agent runs a shell command] --> H{Guard hook: matches a configured lease and isn't wrapped?}
  H -- no --> P[Host's normal permission flow decides] --> R[Command runs]
  H -- yes --> D[Blocked, with: rerun as forge lease db -- cmd]
  D --> W[Agent runs forge lease db -- cmd]
  W --> P2[Host's normal permission flow decides] --> L{Lease free?}
  L -- yes --> X[Run, then release]
  L -- held --> Q[Wait up to 9 min] --> L
  Q -- timed out --> B[Exit 75: busy, held by session X]

Because the hook only ever blocks, it can't get around a permission system: your allow rules, auto mode and T3 Code's approval modes all keep the final say.

What changes for you

  • Nothing, until you add leases or slots to .forge/config.json. Both are opt-in.
  • New commands: forge lease, forge lease list, forge lease check, forge slot, forge slot env.
  • forge init adds one more hook (shell commands, Claude Code and Cursor). It does not add any permission rules.
  • When you configure a db lease, forge evidence runs that touch the database also take turns.

Risks and open questions

  • During an upgrade, a session on the old Forge version and one on the new version won't wait for each other on full test runs (the lock file moved). They're only slower, never wrong.
  • Loose patterns like test can block more than intended. The docs recommend precise patterns, and the block message names the pattern that matched.
  • Codex has no project hooks, so there the protection comes only from wrapped scripts and forge evidence.
  • A lease guarantees taking turns, not safety: if a holder crashes mid-migration, the next one runs anyway.

Out of scope

  • Sessions messaging each other (the T3 Code style).
  • Creating or migrating a database per slot; your project's setup does that using the slot env.
  • Letting more than one session hold a lease at once.
  • T3's own subagent tool bypassing Forge's model policy (logged separately as a finding).
