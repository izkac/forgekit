A deleted log stops blocking a review that really happened

Operator brief — change review-freeze-qualifier

Forge can currently refuse to let you finish a high-risk change that was properly reviewed, because the record of the review helper was cleaned up between two steps. It reads the missing record as "nobody reviewed this" and blocks you — permanently, since the blocked attempt saves nothing and every retry does the same thing.

This teaches Forge to tell "the log was deleted" from "no reviewer ran", by writing down what it saw the first time instead of guessing the second time.

What you'll get

  • A change whose reviewer really ran finishes normally, even if the helper's log was cleaned up in the meantime.
  • A change nobody reviewed is still blocked. That is the whole point of the gate and it does not move.
  • You stop having to talk Forge past a decision it got wrong. Today the only way through is to file a formal waiver saying the review was skipped — against a change that was reviewed. That record was false and it was permanent.

Why it happens

Forge decides who reviewed a change once, at the finish step, and writes the answer down so it survives the logs being cleaned up later. It also has a safety rule: if a later step knows less than the first one did, keep the earlier answer.

That safety rule only applies when the first answer came from the helper's log. Since the last release, many correct answers now come from the review write-up instead — and those get no protection at all. So the later step, seeing an empty log directory, concludes nobody was ever dispatched and overrules a correct answer.

What changes for you

No new commands and nothing to configure. Sessions finished before this change keep behaving exactly as they do today — the new note simply isn't there for them, and Forge treats "not written down" as "unknown", never as "no reviewer".

Risks and open questions

  • The obvious shortcut would be wrong. Simply protecting every earlier answer would fix the symptom and break something real: the review write-up can be edited between the two steps, and a stale reading of it must not outrank a fresh one. One test in this change exists purely to tell the correct fix from that shortcut — without it, the weaker version passes everything and ships looking identical.
  • Two earlier attempts at this same rule were reverted. Both are still pinned by tests, and those tests must pass without their setups being touched. If either needs adjusting, that is the signal this attempt has the same flaw and the work stops.
  • This does not fix the first-pass case. If the log is already gone the very first time Forge looks, there is no earlier answer to compare with, and it will still block. Closing that properly means Forge marking the review write-up itself when it dispatches a reviewer — tracked separately, not attempted here.

Out of scope

  • The request floor from the last release is unchanged.
  • How the review write-up is read is unchanged.
  • The gate's own question — was the final review independent — is unchanged.
