Review stamp at dispatch

TL;DR

When a high-risk change (money, auth, contracts, migrations) is finished, Forge must know whether an outside reviewer actually read it. Today that knowledge lives in two fragile places: the host agent's own dispatch records, which are deleted after a few days, and the review report's wording, which is written by the very party being judged. After this change, the moment a reviewer is dispatched Forge writes its own permanent receipt — a stamp — and reads that receipt instead of parsing prose.

What you'll get

  • A reviewer who genuinely ran can no longer vanish: even after the host deletes its transcripts, the stamp survives and the change still passes the high-risk gate it earned.
  • Verdicts carry a new, honest evidence grade: recorded — stronger than "we read the report's wording", weaker than "the host's live records confirm it". Ledgers and scorecards show which one decided.
  • No new steps. The one command you already run before dispatching a reviewer (forge review-label final) now writes the stamp as a side effect, and also tells you which model to use.
  • The recent anti-forgery fix stays intact: a stamped dispatch that demonstrably did no work still does not certify a review.

How it works

The label command already sits at the exact moment of dispatch and already knows which session it is labelling. It now also resolves the reviewer's model and appends a small JSON record — unit, label, session id, time, model — into the session's own folder, which the host never prunes. When the final verdict is measured, evidence is consulted strongest-first: the host's live records if they can answer; otherwise the stamp; only then the report's wording.

What changes for you

  • forge review-label final additionally reports (on stderr) the stamp it wrote and the model it resolved. Its printed label is byte-identical to today, so nothing that parses it breaks.
  • If you decline a reviewer after the label was issued, record it with --final-review-waived as before — the stamp says a dispatch was intended, not that you were forbidden to change your mind.
  • Old sessions and projects that never stamp behave exactly as today.

Risks and open questions

  • A stamp proves the dispatch moment, not the review itself. If you stamp, decline the dispatch, and the host record is pruned, the change is over-credited. That direction — crediting too generously rather than refusing correct work — is the one this subsystem deliberately errs toward, and the waiver is the prescribed record for declines.
  • When a stamp decides, the report's wording is not read at all — even an honest "I wrote this myself" line. Same doctrine as the host path: the file under suspicion never moves the verdict.

Out of scope

  • Per-group review grading stays on wording (worth ~2 points, no gate).
  • The known wording-rule weaknesses stay open for legacy sessions; they simply carry less traffic as stamps appear.
  • No completion receipt after the review is finished — one step that cannot be forgotten beats two that can.

Work overview

  • 1. Stamp module and writer — the receipt file and the label command writing it (2 tasks).
  • 2. Verdict precedence — host > stamp > wording, with the anti-forgery floor preserved (2 tasks).
  • 3. Gate and consumers — pin the money/auth gate on the new grade; update ledgers, comments and the skill docs (3 tasks).
  • 4. Product-loop acceptance — end-to-end proof against the shipped binary, pruning included (1 task).
